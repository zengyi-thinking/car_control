# Skill 自迭代协议

目标是让 skill 随实证变强，而不是随聊天变长。

## 什么可以进入 skill

只有同时满足以下条件的知识才考虑提升：

1. 已有代码、构建、台架或实测证据，且状态明确。
2. 会改变未来 AI 的文件选择、诊断顺序、设计边界或验证方法。
3. 对多个后续任务有复用价值，而不是当前参数或一次性补丁。
4. 与现有规则不重复；若推翻旧规则，能在同一修改中替换或删除旧内容。

安全关键且已确认的单次事故教训可以直接提升。普通调参经验优先在不同场景重复成立后再提升。

## 什么不能进入 skill

- 当前 PID、速度、阈值、时间点、版本号、引脚或候选标定值。
- 未验证猜测、聊天摘要、完整构建日志和逐次调参流水账。
- 已由当前源码、README或协议文档准确维护的字段副本。
- 只适用于已撤回分支的实现细节。
- 通用 C、Git 或控制理论教程。

这些内容分别留在 `hw_config.h`、协议文档、`CONTINUITY.md`、`decisions.md` 或历史记录。

## 经验候选卡

准备把一次开发经验提升为规范时，先写一张短卡，不直接追加故事：

```text
问题与第一分歧点：
证据和最高验证等级：
已排除或被否定的机制：
适用仓库、模块与条件：
会改变未来哪项决策：
要替换或压缩的旧规则：
目标参考文件：
```

卡片证据不足时先留在项目状态或决策记录。进入 skill 后只保留提炼后的规则，原始日志和参数仍留在项目历史。

## 更新流程

1. 写出新经验的证据、适用范围和会替代的旧规则。
2. 先更新 `Motherboard_Demo/.agents/skills/feiyue-leiqu` 规范源；选择现有最相关参考文件，不默认新建文件。
3. 用一句规则替换一次事故叙述；保留决策方法，删除日期、参数和故事背景。
4. 运行 `scripts/audit-skill.ps1`，修复链接、占位符和体积问题。
5. 运行 `scripts/sync-mirrors.ps1`，把规范源同步到现有飞控、小车与副摄仓库。
6. 再运行 `scripts/audit-skill.ps1 -CheckMirrors` 并检查三个仓库 diff，确认只有 skill/README 等预期文件变化。
7. 不自动提交、推送或发布；由维护者确认。

## 防臃肿预算

- `SKILL.md` 只放路由、核心不变量和通用工作法，建议不超过 160 行。
- 每个参考文件聚焦一个决策域，建议不超过 220 行。
- 全部 Markdown 指令合计建议不超过 1100 行。
- 新增规则时优先压缩或删除一条重复/过期规则。
- 不按日期追加章节；按主题修改现有规则。

超过预算不是机械拆文件，而是先判断内容是否应留在项目文档或历史记忆。只有两个工作模式确实需要不同上下文时才新增参考文件。

## 版本与镜像

- `Motherboard_Demo/.agents/skills/feiyue-leiqu` 是三工程同级存在时的规范源。
- `flight_control`、`car_control` 和 `camera_helper` 保存运行时镜像，使独立克隆和独立工作目录也能自动发现。
- 三份 `name` 保持相同；不要在三个仓库分别演化内容。
- 同步脚本只覆盖 skill 的运行时指令、脚本与 `VERSION`，不复制发布用 README、LICENSE 或 CI，也不修改固件、项目记忆和普通文档。

## 评估 skill 是否真的变好

用真实但只读的任务做前向测试：

- 判断一个新飞行任务应放在哪个核心、实时通道和模块，并列出任务契约。
- 在降落、定时任务、视觉追车和悬停之间加入新模式，验证优先级与抢占清理完整。
- 从一段跨层遥测定位第一分歧点。
- 评估一次 A4/C5 或 B1/B2 改动的影响范围。
- 给出小车提速但保留无人机追赶余量的单变量计划。
- 分析副摄弱识别，同时约束误检和主摄接管。
- 区分“构建通过”和“物理行为已验证”。

如果新规则没有改变文件选择、诊断质量、风险控制或验证完整性，就不值得留在 skill 中。
