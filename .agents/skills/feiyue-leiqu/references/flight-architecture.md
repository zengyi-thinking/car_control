# 飞控架构与任务地图

本文件保存决定代码放置和实时边界的稳定规则。当前启用宏、任务时间、协议版本和参数必须从实时代码、`hw_config.h`、模块地图与当前状态读取，不在这里冻结副本。

## 端到端结构

```text
副摄B2 ─┐
        v
主摄帧 -> CM7_0感知/目标选择 -> 双核共享 -> CM7_1任务仲裁
小车C5 -> CM7_0链路服务 ------^              |
                                               v
                                      引导/估计/控制/混控
                                               |
CM7_1任务反馈 -> 双核共享 -> CM7_0 A4发布 -> 小车执行
```

- CM7_0 拥有主摄流水线、主副摄候选采用、信标身份、显示、A4 与外部视觉通讯编排。
- CM7_1 拥有飞控启动、传感器、状态估计、飞行任务时间轴、模式仲裁、姿态/高度/水平控制和最终电机命令。
- 小车拥有命令仲裁、车体运动成形、麦轮与四轮执行；副摄只提供感知快照。
- 跨核任务语义通过唯一共享内存边界传递，不让两个核心分别维护同一任务倒计时或任务身份。

## 四类执行通道

### CM7_1 高速控制通道

PIT 驱动的固定控制节拍只执行有界工作：

`传感器快照 -> 已缓存任务命令 -> 光流/EKF -> 控制计算 -> 输出提交`

这里可以做短计算、状态更新和确定性寄存器输出。禁止阻塞 I/O、显示、字符串、长扫描、整帧协议处理和复杂任务规划。新增代码必须说明最坏执行时间和是否改变固定顺序。

### CM7_1 低速服务通道

主循环处理共享视觉包、较慢传感器服务和可能阻塞的电调传输。低速服务只生成缓存或快照；高速通道消费已经成形的数据。跨通道共享值要有原子快照或短临界区，不能边读边改复合状态。

### CM7_0 视觉帧通道

相机新帧到达后执行纯视觉管线、任务目标选择、共享发布和分频显示。显示、状态文本与 UART 服务不得阻塞目标发布。显示结果、稳定发布与当前真实测量保持不同语义。

### 中断接收通道

UART/GPIO ISR 只收字节、清标志、采样时间或推进有界解析器。不得在 ISR 中运行图像算法、任务状态机、外设大事务或日志格式化。

## 分层放置规则

| 需求 | 所属层 | 不应放入 |
|---|---|---|
| 启动、任务仲裁、模式生命周期 | `application` | ISR、协议编解码、控制器内部 |
| 姿态、高度、EKF、运动学、视觉纯计算 | `algorithm` | 显示、UART、任务身份 |
| 传感器、电机、共享内存、线协议 | `hardware` | 任务时间轴、目标选择策略 |
| 核入口、IRQ、周期触发 | `user` | 业务状态机、长期运行态 |
| 当前参数与功能开关 | `hw_config.h` | skill、历史文档、多处副本 |

新增模块优先使用私有状态和窄接口。应用层输出任务意图，算法层输出纯计算结果，硬件层翻译物理与线语义；下层不能反向决定任务策略。

## 当前任务栈的读取方式

开始任务前从当前模块地图和源码核对，但通常应区分四层：

1. 飞控生命周期：启动校准完成后才进入运行阶段。
2. 顶层任务仲裁：安全/降落类任务优先于定时任务，定时任务优先于普通视觉追车，最后回到悬停或零速保持。
3. 引导状态：追车内部再区分保持、追赶和制动，不等于顶层任务状态。
4. 控制执行：姿态、高度、Yaw 与混控只消费有界目标，不知道业务故事。

现有文件名可能小于其实际职责。例如视觉追踪模块可能同时承担顶层仲裁；新增任务不能据此在不同文件再建一套优先级。任务增多时应先收口唯一仲裁点，再考虑重命名或提取 mission manager。

## 修改前的架构检查

- 谁拥有最终决定，谁只提供测量或执行？
- 代码运行在高速、低速、视觉帧还是 ISR 通道？
- 输入是否为完整、新鲜、可信且被任务选中的快照？
- 输出是任务意图、控制目标、协议字段还是物理执行？
- 是否出现两个状态机同时控制同一目标或执行器？
- 是否新增跨核/跨仓语义，需版本、兼容和配套烧录？
- 是否复制了当前源码中的历史集中结构，而不是遵守目标分层？

对结构关系使用当前会话提供的代码图工具；工具不可用时从入口、头文件和目标源码建立调用链。不要只凭模块地图推断实时代码已经一致。
